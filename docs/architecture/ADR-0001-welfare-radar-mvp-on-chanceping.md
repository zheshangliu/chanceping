# ADR-0001：企业福利商机雷达 MVP 复用 ChancePing

- 状态：已接受
- 日期：2026-07-11
- 范围：`fuli.chanceping.com` 公开 MVP

## 决策

企业福利商机雷达的公开 MVP 继续使用 ChancePing 当前的 TypeScript、Hono、静态 Web UI、JSON 运行时存储和 systemd 部署方式。

V1.2 整合包仍是业务字段、事实边界、来源范围和验收规则的权威基线。PostgreSQL、Redis、Celery、MinIO、RBAC、审计和完整销售工作台延后到内部 MVP，在引入前另做迁移 ADR。

## 原因

当前目标是先验证真实公开来源到机会卡和报告的垂直链路。ChancePing 已有公开 AI 赛事页面、公共 Feed、调度、报告和 SWAS 部署能力，复用这些能力可以避免建设第二套产品外壳。

## MVP 边界

- 首个来源仅 `OFF-SZ-004`，随后才增加 `OFF-SZ-005`、`OFF-SZ-003`。
- 不使用外部 LLM 分类。
- 仅公开官方采购公告明确披露的采购联系人、办公电话和联系地址，并保留字段级来源证据；不采集私人地址、员工名单或配送地址。
- 聚合页只产生候选；公开卡必须能回到官方详情页。
- 预算、截止、采购人和状态分别记录证据状态；未知不得视为已核验。
- 结果、合同、终止和已截止项目不得进入当前有效列表。
- 运行时证据写入 `data/welfare-evidence/`，该目录不进入 Git。

## 已知差异与修正

V1.2 PostgreSQL DDL 的 `radar.organizations` 重复声明 `country_code`。将来导入 Alembic 前必须删除重复列并增加迁移测试，不能直接执行原 SQL。

V1.2 文档称 G0 为 20—35 人日，但任务表中标为 G0 的任务合计约 50.5 人日。本 ADR 将“公开 MVP 垂直切片”和“完整内部 G0/G1”分开估算。

## 后果

公开 MVP 能快速上线，但当前 JSON 证据存储不等于企业级不可变证据库。对外页面必须明确其为公开信息整理，内部销售评分和正式 R4/R5 工作流在 PostgreSQL 迁移完成前不宣称已实现。
