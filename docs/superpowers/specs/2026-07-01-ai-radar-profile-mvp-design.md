# ChancePing AI 雷达画像 MVP 核心闭环设计

> 状态：待 Jason 评审  
> 日期：2026-07-01  
> 适用范围：当前 `rescue/mvp-codex` 分支后续 MVP 工作  
> 前置文档：`2026-06-30-mvp-ux-rescue-design.md`

## 1. 这次重新定义什么

ChancePing 的 MVP 不是一组按行业硬编码的雷达模板，也不是一个让用户填写搜索参数的工具。

MVP 的核心产品能力应定义为：

```text
把客户非标准、零散、非结构化的表达或文件，
转化成一份客户确认过、可执行、可复用的雷达画像，
再依据画像持续搜索、筛选、评分并交付可行动机会。
```

行业和角色可以无限变化：乒乓球选手、补贴申报公司、研学文旅公司、婚庆公司、员工福利公司、活动布置公司，都必须通过同一个通用画像引擎处理。产品不能依靠为每种客户新增一个模板来扩展。

首页保留少量示例，仅用于新手教育。示例不是产品分类，也不是搜索能力边界。

## 2. MVP 的客户承诺

客户只需要完成四件事：

1. 说出或上传自己正在寻找的机会。
2. 与 AI 补充少量真正影响结果的信息。
3. 确认 AI 整理出的雷达画像。
4. 查看本轮机会，并在有价值时保存为长期雷达。

产品负责完成：

1. 理解客户身份、目标和约束。
2. 将非结构化需求编译成结构化雷达画像。
3. 将画像编译成搜索计划并执行多源搜索。
4. 对结果去重、验证、匹配、评分和分级。
5. 以机会卡片和 Markdown 报告交付结论。
6. 保存画像、运行、机会和报告之间的完整关联。

## 3. 产品原则

### 3.1 一个入口，不预设客户属于哪个行业

首页主输入区同时接受：

- 自由文本。
- 从文件中解析出的文本。
- 客户指定的官网、平台名或 URL。
- 对上一轮 AI 追问的补充回答。

用户不需要先选择“AI 赛事”“政策申报”或其他雷达类型。行业、机会类型和行动目的由 AI 从上下文中识别，并由用户在画像确认阶段校正。

### 3.2 先理解，再搜索

原始输入不能直接成为搜索 query。必须先形成雷达画像，并由客户确认。

```text
原始表达不是雷达
雷达画像不是搜索结果
搜索结果不是最终机会
```

三者通过明确的数据契约衔接，避免把一句模糊描述直接扩写成看似精确但实际错误的搜索任务。

### 3.3 AI 对话，不是机械问卷

澄清过程采用自然对话，AI 每轮只追问一个最关键问题，并说明自己已经理解了什么。

推荐交互：

```text
AI：我明白你是一家研学文旅公司，想寻找可能采购研学服务的单位。
    还差一个最影响搜索结果的信息：你更希望先找国企、学校，还是两类都找？
```

禁止的交互：

- 一次丢出六个固定字段。
- 对用户已经说过的内容再次提问。
- 为了提高完整度分数而询问不影响搜索的问题。
- 无限追问，始终不生成画像。

MVP 默认最多澄清 3 轮，每轮 1 个关键问题。每轮都提供 `先按默认理解继续`。达到上限后，系统必须生成画像，并把未确认内容写为可见的“默认假设”。

### 3.4 画像由客户确认后才可运行

画像确认卡使用客户语言展示，不暴露 `spec`、provider、source strategy 等技术字段。

客户看到：

- 你是。
- 你想盯。
- 优先看。
- 地域与时间。
- 排除。
- 指定信号源。
- 默认假设。

客户可以：

- `确认，开始盯机会`。
- `我再改一下`。

### 3.5 结果必须可行动、可验证

正式机会至少要有：

- 可理解的机会标题。
- 为什么适合当前客户。
- 截止时间或时间状态。
- 下一步建议动作。
- 可打开的真实来源。
- S、A、B、C 级之一。

没有可验证来源的内容不能包装成正式机会，只能进入“待复核线索”或被过滤。

## 4. 完整客户流程

### 4.1 通用自由输入路径

```text
首页自由表达或上传文件
→ AI 提取已知事实、缺失信息和冲突
→ 判断是否需要澄清
→ 0 至 3 轮自然对话
→ 生成雷达画像草案
→ 客户确认或修改
→ 编译搜索计划
→ 多源搜索、抓取、去重和验证
→ 画像匹配、过滤、评分和分级
→ 展示机会卡片与报告摘要
→ 展开、复制或下载 Markdown
→ 可选：保存为长期雷达
```

### 4.2 示例路径

首页仅保留 3 个左右差异明显的示例，标题统一放在“试试看这些例子”下。

示例点击后把一段完整的自然语言需求填入通用输入链路。它可以跳过澄清，但仍显示画像确认卡，并允许用户调整。

示例不直接绑定旧的固定 `RadarKind`，也不使用独立业务代码。

### 4.3 长期雷达路径

客户看到首次结果后点击：

```text
保存为长期雷达，之后持续盯
```

系统执行：

```text
创建 custom 雷达
→ 保存已确认 RadarRequirementSpec
→ 激活雷达
→ 立即运行一次该雷达
→ 机会入库并绑定 radarId/radarIds
→ 生成绑定 radar_id + run_id 的 Markdown 报告
→ RadarRun.reportId 回写
→ 我的雷达可查看本次机会和报告
```

首次即时结果可以作为预览，但保存动作必须以绑定长期雷达的运行记录为准。MVP 优先保证数据关系正确，必要时允许保存后重新运行一次。

免费用户最多保存 3 个长期自定义雷达。示例预览和未保存的即时结果不占配额。

## 5. 通用雷达画像

### 5.1 唯一事实来源

`RadarRequirementSpec` 继续作为可执行雷达画像的唯一事实来源，不另建一套平行画像 Schema。

现有结构已覆盖 MVP 所需的主要维度：

- `client_profile`：客户身份、行业、业务和能力。
- `core_goals`：主要目标、成功定义和行动意图。
- `opportunity_scope`：机会类型、必须条件和排除类型。
- `region_scope`：地域边界。
- `keyword_strategy`：中英文核心词、扩展词和负面词。
- `source_strategy`：官方来源、平台、手动来源和用户 URL。
- `filter_rules`：必须包含、必须排除及人工复核条件。
- `scoring_rules`：画像匹配和评分规则。
- `report_requirements`：报告格式和内容要求。
- `requirement_confidence`：需求理解可信度。
- `questions_to_confirm`：仍需确认的问题。
- `confirmation_status`：画像确认状态。

前端只展示这些字段的客户语言摘要，不直接渲染原始 Schema。

### 5.2 画像生成输出

`POST /api/radars/generate` 应返回足够支撑对话和确认卡的数据：

```ts
interface RadarGenerateResponseData {
  spec: RadarRequirementSpec;
  suggestedName: string;
  completeness: number;
  requirementConfidence: number;
  questionsToConfirm: QuestionToConfirm[];
  profileSummary: {
    identity: string;
    target: string;
    priorities: string[];
    regionsAndTime: string;
    exclusions: string[];
    sourceHints: string[];
    assumptions: string[];
  };
}
```

`completeness` 表示字段是否具备，`requirementConfidence` 表示系统是否真的理解。两者不能混为一个数值。填满错误字段不等于理解正确。

### 5.3 需求判断规则

内部优先检查六个维度：

1. 客户或行动主体是谁。
2. 想获得哪类机会。
3. 地域或业务范围。
4. 时间窗口。
5. 发现后准备采取什么行动。
6. 排除条件和指定来源。

这些维度是 AI 的判断框架，不是必须逐项询问的表单。

建议决策：

- 可信度大于等于 85：直接生成画像确认卡。
- 可信度 60 至 84：进入对话澄清，每轮询问一个高价值问题。
- 可信度低于 60：先请用户补充最关键的一句背景，再继续判断。
- 示例路径：可跳过澄清，但不可跳过画像确认。
- 用户选择默认继续：停止追问，以明确假设补齐画像。

### 5.4 文件输入边界

MVP 复用现有 `/api/upload` 和文件解析器，支持现有 PDF、Word、Excel 和图片类型，单文件上限保持 20 MB。

文件的作用是补充客户需求，不是直接成为搜索结果。解析文本与用户文字一起进入同一个对话上下文，并在画像中区分：

- 用户明确表达的事实。
- 从文件提取的事实。
- AI 做出的默认假设。

MVP 不承诺任意文件类型，不处理音视频、压缩包、加密文件或复杂批量知识库。解析失败时保留用户已输入的文字，并允许重新上传或继续对话。

## 6. AI 澄清会话设计

### 6.1 会话状态

一条会话至少包含：

```ts
interface RadarDiscoverySession {
  conversationId: string;
  originalInput: string;
  uploadedText: string[];
  turns: Array<{ role: "user" | "assistant"; content: string }>;
  currentDraft: RadarRequirementSpec;
  confidence: number;
  assumptions: string[];
  clarificationCount: number;
  status: "understanding" | "clarifying" | "confirming" | "confirmed";
}
```

MVP 会话可以继续使用进程内存，但必须清楚提示刷新可能丢失未确认内容。画像一旦确认并保存，就必须进入持久化雷达数据。

### 6.2 每轮 AI 输出

AI 每轮返回：

- 对当前理解的一句自然语言复述。
- 最需要确认的一个问题，或画像已可生成的判断。
- 当前草案和置信度，供系统内部使用。
- 默认继续时将采用的假设。

前端不能自行用狭窄关键词表承担主要语义判断。前端只做异常兜底，例如后端低置信度却没有返回问题时，按缺失维度生成一个通用补充请求。

### 6.3 冲突和修改

当文件与用户后续回答冲突时，以用户后续明确回答为准，并在画像确认卡中显示最终采用的理解。

客户点击 `我再改一下` 后，回到同一会话补充一句自然语言，不打开原始 JSON 编辑器。修改后重新生成画像确认卡，不直接开始搜索。

## 7. 从画像到搜索计划

### 7.1 搜索计划是内部执行对象

确认后的画像编译为一次 `RadarSearchPlan`：

```ts
interface RadarSearchPlan {
  radarId?: string;
  runId: string;
  goals: string[];
  queries: Array<{
    query: string;
    language: "zh" | "en";
    region?: string;
    timeWindow?: string;
    sourceDomain?: string;
  }>;
  sourceHints: string[];
  exclusions: string[];
  maxCandidates: number;
}
```

搜索计划不需要作为客户编辑页面。客户只确认“找什么”，系统负责决定“怎么搜”。

### 7.2 多源搜索策略

MVP 运行顺序：

1. 根据画像生成中英文关键词组合。
2. 使用当前可用 Provider 做常规搜索。
3. 对客户提供的 URL 或域名追加定向搜索。
4. 对来源名称生成带站点或机构名的补充 query。
5. 合并、规范化并按 URL/标题去重。
6. 抓取候选页面并提取关键事实。
7. 进入过滤、匹配和评分。

`custom` 雷达不得再默认映射为 `ai_competition`。Provider 选择和 query 生成必须依据画像、来源提示和可用能力，而不是依据有限行业枚举。

### 7.3 API 接入范围

本阶段不追求一次接入所有外部 API。MVP 要求：

- 保留并统一现有 Provider 接口。
- 至少打通一个真实搜索 Provider 的本地 live 验收。
- 至少打通一个真实 LLM 的画像生成和匹配验收。
- `api.env` 仅本地显式加载，不提交，不在生产默认加载。
- Provider 失败时保留明确状态，不能伪造结果或悄悄替换成不相关 Mock。

用户已有的 API 清单可以用于后续选择首个 live 组合，但不是画像主链路开始实施的前置条件。

## 8. 匹配、过滤和分级

### 8.1 两阶段判断

候选结果先通过硬过滤，再进行软匹配：

硬过滤示例：

- 已明确截止。
- 与地域、对象资格或机会类型冲突。
- 命中必须排除条件。
- 链接无效且无其他可验证来源。

软匹配维度：

- 客户适配度。
- 行动意图强度。
- 来源和证据可信度。
- 时间紧迫性。
- 预计行动成本。

### 8.2 客户分级

延续现有 ChanceScore 阈值：

- S：90 分及以上，优先立即行动。
- A：80 至 89 分，值得重点推进。
- B：65 至 79 分，可以评估或准备。
- C：50 至 64 分，低优先级观察。
- 50 分以下：不进入正式机会卡片，可进入报告的“暂不推荐”部分。

客户只看到等级、理由和建议动作。内部五维分数可以保留用于调试和后续优化，但不作为 MVP 主界面负担。

### 8.3 评分解释

每个正式机会必须生成与当前画像相关的 `whyFit`，不能使用通用套话。解释至少引用一个具体匹配点，例如地区、资格、业务目标、时间窗口或指定来源。

## 9. 结果与报告

### 9.1 机会卡片

信息顺序固定为：

1. 等级和标题。
2. 为什么适合你。
3. 截止时间或时间状态。
4. 建议动作。
5. 官方来源。

来源链接必须使用搜索和验证阶段保留的原始 URL，不能由 LLM 编造。

### 9.2 Markdown 报告

页面默认展示：

- 本轮总判断。
- 最值得行动的 1 至 3 个机会。
- 本周行动清单。
- 下一轮监控重点。

完整 Markdown 通过 `查看完整 Markdown 报告` 展开，并提供 `复制 Markdown` 和下载 `.md`。

完整报告沿用已确认的结构：雷达画像、本轮机会总表、重点机会详解、观察池、行动清单、下一轮监控和来源索引。

报告至少包含一个真实机会标题；若没有合格机会，应生成“本轮无合格机会”的监控报告，而不是伪造机会来填满版面。

## 10. 现有代码的保留与调整

### 10.1 直接复用

- `RadarRequirementSpec` 及其校验器。
- `/api/upload` 与现有文件解析路由。
- `ConversationManager` 的会话骨架。
- `RadarGenerator`、`RadarSpecCompiler` 的职责边界。
- `SearchOrchestrator` 和 Provider 适配层。
- ChanceScore 评分模型。
- 雷达、运行、机会和报告存储。
- 当前结果页、画像确认卡和 Markdown 展示的可用部分。

### 10.2 必须调整

- 画像生成提示词从“字段缺失时合理推断”改为“区分事实、未知和假设”。
- `/api/radars/generate` 返回置信度、待确认问题和客户语言摘要。
- 将澄清判断从前端关键词规则迁回后端 AI/领域逻辑。
- Mock 生成器覆盖通用目标，不再仅特判乒乓球并默认 RPA。
- `custom` 雷达不再映射到 `ai_competition`。
- 示例统一走自然语言和画像引擎，不再成为独立雷达类型。
- 搜索 query 由已确认画像生成，而不是从首页一句话直接拼接。
- 保存长期雷达时完成 `radar_id + run_id + reportId` 闭环。

### 10.3 暂不删除

旧的固定 RadarKind、编辑器、机会库和独立报告页暂时保留，以避免破坏 V1.5/V1.6。它们从普通客户主导航隐藏，并逐步改成兼容通用画像的内部能力。

## 11. 错误和降级

### 11.1 LLM 不可用

- 显示“暂时无法理解需求”，保留用户原始输入和已上传文本。
- 允许重试，不生成错误画像。
- Mock 模式必须明确标记为演示，返回与输入语义一致的结果。

### 11.2 搜索 Provider 不可用

- 展示失败状态和可重试操作。
- 其他 Provider 可继续，但报告记录本轮实际完成的搜索范围。
- 不用 `example.com` 或无关行业数据伪装成功。

### 11.3 没有合格机会

展示可行动建议：

- 放宽地区或时间。
- 减少排除条件。
- 增加指定信号源。
- 保存为长期雷达继续监控。

### 11.4 链接不可访问

链接验证失败的候选进入待复核区，不作为 S/A/B/C 正式机会。客户提供的来源无法访问时保留原值并标记，不擅自改写。

### 11.5 文件解析失败

保留文本输入和其他成功解析内容。界面说明具体文件失败，并允许移除或重新上传。

## 12. MVP 验收场景

### 12.1 模糊个人需求

输入：

```text
我想盯乒乓球比赛
```

预期：

- 不直接搜索。
- AI 用自然语言确认角色、范围或行动目的中最关键的一项。
- 最多 3 轮后生成画像，并显示默认假设。
- 客户确认后才搜索。

### 12.2 完整个人需求

输入：

```text
我是乒乓球选手，想盯未来30天内国内外可报名的乒乓球比赛，
优先看 ITTF、WTT、中国乒协官网，排除培训广告。
```

预期：

- 直接生成画像确认卡。
- 画像保留角色、时间、地域、来源和排除条件。
- 确认后返回与乒乓球相关且链接可访问的机会。

### 12.3 企业客户线索需求

输入：

```text
我们是一家研学文旅公司，正在寻找有研学、红色教育、团队学习需求的国企和企业，
希望找到近期公开采购、招标、合作征集或活动计划，优先广东和周边地区。
```

预期：

- 识别为寻找客户和合作线索，不误判为比赛。
- 画像包含目标客户、采购或合作信号、地域与行动目的。
- 搜索计划覆盖招标采购、合作征集、职工培训和企业活动等信号。
- 报告给出联系或投标建议，而不是报名比赛建议。

### 12.4 文件补充需求

输入：一句简短目标，加一份公司介绍或历史项目文件。

预期：

- 文件内容补充客户能力和目标客户信息。
- AI 不把文件中的案例名称误认为当前必须搜索的机会。
- 画像确认卡标出必要默认假设。

### 12.5 示例教育路径

点击 `AI 赛事` 示例。

预期：

- 示例填入一段完整自然语言需求。
- 可跳过澄清并进入画像确认。
- 客户可以点击 `我再改一下`。
- 后续仍走同一通用搜索、评分和报告链路。

### 12.6 长期雷达闭环

保存任一已确认画像。

预期：

- 免费用户在未满 3 个时保存成功。
- 雷达立即激活并运行。
- `opportunityCards.length > 0`，或明确记录本轮无合格机会。
- 正式机会入库并包含当前 `radarId` 或 `radarIds`。
- 报告绑定 `radar_id + run_id`。
- `RadarRun.reportId === reportId`。
- 我的雷达能看到本次机会和报告。
- 页面刷新后数据仍存在。

## 13. 测试策略

### 13.1 单元测试

- 通用画像提取，不同角色不会回退到 RPA 或 AI 赛事。
- 事实、未知项和默认假设分离。
- 置信度阈值和最多 3 轮规则。
- 搜索计划从画像生成正确的目标、地域、来源和排除词。
- 评分等级边界和无来源降级。
- 免费用户 3 个雷达配额。

### 13.2 API 测试

- `/api/radars/generate` 返回完整画像摘要和澄清信息。
- 用户回答后，同一上下文重新生成画像。
- 上传解析文本进入画像生成上下文。
- 保存、激活、运行和报告绑定成功。

### 13.3 浏览器验收

浏览器 Smoke Test 覆盖：

```text
首页
→ 模糊输入
→ AI 一次一问
→ 默认继续或回答
→ 画像确认
→ 搜索 loading
→ 机会卡片
→ 报告摘要
→ 展开完整 Markdown
→ 保存长期雷达
→ 我的雷达
→ 刷新后仍存在
```

必须另跑研学文旅客户线索场景，证明产品能力不是依靠乒乓球特判。

`verify-live-mvp` 不加入 `verify:all`，仅在 Jason 明确允许并且本地 `api.env` 已准备好时执行。

## 14. 分阶段交付建议

本设计应拆成小里程碑，不一次性重写全部系统。

### Milestone A：通用画像与 AI 澄清

- 统一画像生成响应契约。
- 改造提示词和 Mock，消除行业硬编码回退。
- 后端输出事实、未知、假设、置信度和一个关键问题。
- 前端改成最多 3 轮的一次一问。
- 文件输入进入相同上下文。
- 完成乒乓球与研学文旅两类对照验收。

### Milestone B：画像驱动的搜索与评分

- 新增或明确 `RadarSearchPlan`。
- `custom` 搜索摆脱 `ai_competition` 默认。
- 画像关键词、地域、来源和排除规则进入搜索。
- 验证真实 URL、去重和 S/A/B/C 分级。
- 机会解释与当前画像绑定。

### Milestone C：报告与长期雷达闭环

- 固化报告摘要和完整 Markdown。
- 保存后创建、激活并运行长期雷达。
- 完成机会、run、report 的绑定和持久化。
- 免费用户 3 个雷达配额。
- 浏览器完成端到端回归。

每个 Milestone 完成后先由 Jason 浏览器验收，再进入下一个。原 Task 5-8 继续暂停，直到本设计对应的基础 MVP 闭环通过。

## 15. 本轮明确不做

- 为每个行业内置大量模板。
- 雷达市场。
- 团队协作。
- 付费体系。
- 自动订阅和消息推送。
- V1.7 来源透明完整后台。
- V1.7 反馈调优。
- 完整来源管理后台。
- 自动抓取任意网站的通用爬虫平台。
- 一次接入所有搜索与 LLM API。
- 大规模 UI 或品牌视觉重构。
- 删除 V1.5/V1.6 旧能力。

## 16. 外部 API 与既有任务模板的处理决定

### 16.1 外部 API

现在可以提供 API 文件用于后续 live 验证，但实施时只选择一个搜索 Provider 和一个 LLM 作为首个可验证组合。密钥不写入文档、代码、测试输出或 Git 历史。

### 16.2 既有任务模板

建议先提供 3 至 5 份差异明显、质量较高的任务模板，而不是全部迁移。

它们只作为：

- 画像生成 Prompt 的少量示例。
- 自动化测试样例。
- 搜索计划质量参照。
- Markdown 报告风格参照。

它们不作为客户可见的行业模板库，也不决定产品能服务哪些角色。

## 17. 最终成功判断

当一个此前从未预设过的新客户角色出现时，ChancePing 仍然能够：

1. 听懂客户在找什么。
2. 在必要时自然地追问。
3. 生成客户认可的雷达画像。
4. 按画像搜索并筛出可验证机会。
5. 给出与客户目标相关的等级和行动建议。
6. 生成可复制、可下载的 Markdown 报告。
7. 保存为可重复运行的长期雷达。

达到这七点，才说明 MVP 的基础能力成立；模板数量、页面数量或 Provider 数量都不能替代这个判断。
