# GPT 雷达 vs ChancePing MVP 对照分析

日期：2026-07-01  
状态：已用 4 份调研、4 份实际报告及官方来源抽查验证，待 Jason 评审  
目的：判断 ChancePing 是否应改为“聊天即产品”，以及现有 MVP 核心闭环设计中哪些内容应保留、移出主路径或改造。

## 1. 执行结论

结论是：**ChancePing 应把 MVP 改成“聊天优先”，但不应做成“只有聊天”。**

推荐形态：

```text
聊天是唯一主要交互界面
+ 雷达画像是后台长期记忆
+ 搜索计划、来源验证和评分在后台执行
+ 机会卡片和 Markdown 是聊天中的结构化交付物
+ 我的雷达负责保存、重跑和历史，不负责复杂配置
```

四份 GPT 雷达调研和四份实际报告都证明了一件事：用户感受到的流程非常简单，只需要在聊天中描述需求，之后说“执行本周雷达”，系统就搜索并生成 Markdown。但 GPT 并不是省略了雷达画像、搜索计划、评分和报告模板，而是把它们隐藏在对话上下文和平台工具背后。

ChancePing 不应复制 GPT 的黑盒和上下文脆弱性。它应复制 GPT 的低操作成本，同时用结构化存储、可重复运行、来源证据和历史记录弥补 GPT 的不足。

一句话定位建议：

> ChancePing 是一个能记住你在找什么、可以反复执行并交付可验证机会报告的聊天式 AI 雷达。

## 3. 四个 GPT 雷达实际在做什么

四份调研的行业完全不同，但后台工作流高度一致。

```text
用户自然语言或上传文件
→ 从聊天历史和项目上下文恢复长期画像
→ 判断本次消息是修改需求还是执行命令
→ 按画像拆分搜索主题
→ 生成中文、英文或其他语言查询词
→ 搜索并打开部分重点网页
→ 提取机会字段
→ 合并、去重、判断时效和来源
→ 结合用户业务做匹配与风险判断
→ 使用该雷达自己的评分模型排序
→ 生成行动建议和 Markdown 文件
```

因此，“聊天即产品”只描述了用户界面，不代表后台不需要结构化系统。

### 3.1 四个雷达共有的长期画像字段

- 服务对象或项目是谁。
- 想找什么类型的机会。
- 地域和语言范围。
- 时间窗口。
- 最终行动目的。
- 优先条件。
- 排除条件。
- 固定来源和官网。
- 评分与排序偏好。
- 报告结构和执行频率。
- 默认假设。

这些字段与当前 `RadarRequirementSpec` 的主体结构基本一致，说明“雷达画像”方向正确。

### 3.2 四个雷达共有的执行能力

- 识别“执行本周雷达”“跑一遍”“输出 Markdown”等运行意图。
- 不重复询问已经在历史上下文中确认的需求。
- 将一个雷达拆成多个搜索主题。
- 生成多语言和站点限定查询。
- 优先使用官方来源，再用媒体和聚合页补充。
- 对过期、资格不符、来源不足的内容降级或排除。
- 生成“为什么适合我”和下一步动作。
- 生成适应该行业的 Markdown 报告。

### 3.3 四个雷达共有的局限

- 画像主要依赖当前对话、项目上下文或平台记忆，新会话可能丢失。
- “执行本周雷达”并不总是完整扫描全部固定来源，部分调研明确只复核了代表性来源。
- 网页打不开时有时使用搜索摘要作为辅助证据。
- 评分虽然有权重，但很多子分由模型主观给出，缺少可回放的评分证据。
- 四份文档的 S/A/B/C 阈值不一致。
- 搜索、打开、抽取、淘汰的完整日志没有作为稳定数据保存。
- 没有真正的定时运行、历史去重、持久化机会库和自动提醒。
- 报告中的“业务机会”有时是从新闻或公司动态推断，不等于已经确认存在岗位、采购或报名入口。

## 4. 逐项对照表

| 维度 | GPT 雷达表现 | ChancePing 当前设计/实现 | 判断 |
|---|---|---|---|
| 第一入口 | 直接聊天 | 首页输入框，之后跳结果面板 | GPT 更自然，应改为聊天主界面 |
| 需求表达 | 可连续说话、补文件 | 文本输入 + 文件入口 | 能力方向正确，交互需合并 |
| 澄清方式 | 结合上下文自然追问 | 前端关键词判断后一次显示最多 3 个问题 | 当前偏机械，应改为 AI 一次一问 |
| 画像可见性 | 通常隐含，必要时总结 | 独立画像确认卡 | 画像应保留，但改成聊天内摘要 |
| 画像持久化 | 依赖对话/项目记忆，脆弱 | 可保存 `RadarRequirementSpec` | ChancePing 明显更可靠，应保留 |
| 再次运行 | 说“执行本周雷达” | 我的雷达点击运行或重新输入 | 应支持自然语言命令和快捷按钮 |
| 执行状态 | 通常只看到模型正在工作 | 有理解、搜索、报告 loading | 应保留，并放进聊天时间线 |
| 搜索计划 | 后台隐式生成 | 设计了 `RadarSearchPlan` | 应保留在后台，不做配置页 |
| 查询词 | 多主题、多语言、site 限定 | 当前仍受固定类型和简单 query 影响 | 必须改造成画像驱动 |
| 指定来源 | 从长期上下文和固定源读取 | Source Hints MVP-light | 方向正确，应支持聊天添加和长期保存 |
| 搜索覆盖 | 灵活但不保证完整 | Provider 编排可重复 | ChancePing 应把覆盖范围和失败状态保存 |
| 来源层级 | 官方 > 政府 > 媒体 > 聚合 > 社交 | 已有来源和证据结构 | 保留，但 MVP 只展示必要结果 |
| 网页验证 | 会打开重点网页，但可能只读摘要 | Jina/网页读取与证据抽取已存在 | 应加强字段级证据状态 |
| 机会定义 | 因行业而变 | 当前主要围绕比赛机会卡 | 必须泛化为比赛、线索、采购、岗位等 |
| 机会语义 | 确定机会、线索、案例、信号和淘汰项常混在报告中 | 当前主要用统一机会对象 | 应新增机会类型，不能只靠证据状态区分 |
| 结果阶段 | 推荐、观察、淘汰或 Attack/Hold/Archive | S/A/B/C/D 和机会卡 | 需要区分等级与行动状态 |
| 评分模型 | 每个雷达有自己的维度 | 一个通用 ChanceScore | 应采用“通用门槛 + 雷达专属评分策略” |
| 评分解释 | 阿柴报告有完整子分，其他报告多为总分和文字判断 | 当前评分解释能力有限 | 每个总分必须能回放子分、规则和证据 |
| 评分阈值 | 多份文档不一致 | 当前统一 90/80/65/50 | 产品应统一等级阈值，画像只定义维度和权重 |
| 风险判断 | 垂直化很强，如版权、费用、合规 | 当前通用风险字段有限 | 应让画像生成风险策略，但先做轻量版本 |
| 为什么适合我 | 结合项目历史，个性化较强 | 已要求 `whyFit` | 保留，并要求引用具体画像字段 |
| 行动建议 | 参赛、外联、建人才池、做材料 | 当前常出现“了解即可” | 必须由行动目的和机会缺口共同生成 |
| 报告结构 | 每个雷达不同，但有共同骨架 | 当前偏统一 Markdown 模板 | 改为公共骨架 + 画像生成的垂直章节 |
| 项目准备度 | 实际报告会评估材料缺口、包装方案和可执行程度 | 当前没有稳定对象 | 应作为画像与机会之间的动态快照保存 |
| 字段级证据 | 报告常用一个链接支撑整条记录 | 已有来源结构但粒度不足 | 时间、费用、资格、权利义务等分别绑定证据 |
| 文件交付 | 直接生成 `.md` | 可展开、复制、生成报告 | 保留并补下载文件 |
| 机会卡片 | GPT 主要在表格/Markdown 中展示 | ChancePing 有卡片能力 | ChancePing 更适合快速浏览，应保留 |
| 历史记录 | 依赖聊天和文件 | 有雷达、run、机会、report 存储 | ChancePing 核心优势，必须保留 |
| 无结果处理 | 仍输出监控结论和准备动作 | 已设计空结果建议 | 保留，改成聊天式回复 |
| 工具失败 | 通常在报告中口头说明 | 有 Provider 降级和失败状态 | 保留并生成运行回执 |
| 用户控制感 | 说一句话即可 | 需要跨多个 UI 状态 | 主路径应显著收敛 |
| 可审计性 | 有自述，但不稳定 | 可以保存 run 和来源 | ChancePing 应在后台形成真正执行日志 |
| 多行业扩展 | 靠模型上下文和单独雷达 Prompt | 当前 Schema 通用，但 Mock 和路由仍硬编码 | 数据结构可用，生成和搜索实现必须泛化 |

## 5. 对实际 GPT 周报的验证判断

### 5.1 做得好的部分

实际跨境金融报告具有明显客户价值：

- 开头直接给本周业务判断，不先解释系统功能。
- Top 15 表把公司、触发信号、岗位、来源、联系人角色、候选人关键词和动作放在一起。
- 报告能根据猎头业务生成商机、交付和线索完整度三个评分。
- 后续章节不是重复列表，而是把线索转为 BD 话术、人才池和实习生任务。
- 结果与“本周要做什么”连接紧密，远强于普通搜索结果摘要。

这说明 ChancePing 的交付目标不应只是“找到链接”，而应是：

```text
将信号转成客户当前可以执行的动作。
```

### 5.2 需要谨慎的部分

报告同时混合了四种不同证据状态：

1. **已确认机会**：存在明确报名、岗位、采购或活动入口。
2. **业务线索**：存在公司动态或市场信号，值得 BD，但需求尚未确认。
3. **观察信号**：行业趋势、IPO、招聘会或岗位样本。
4. **模型假设**：根据公司业务推断可能需要某类岗位。

例如，HKEX 招股书可以证明 Momenta 正在进行全球发售，但不能单独证明它正在招聘报告列出的全部岗位。IPO 可以作为 BD 触发信号，不应被标为已确认招聘机会。

因此 ChancePing 必须新增客户可理解的状态：

| 状态 | 含义 |
|---|---|
| 已确认机会 | 有官方报名、采购、岗位或合作入口 |
| 可行动线索 | 有可靠触发信号，值得联系确认 |
| 观察信号 | 值得继续追踪，但本周不行动 |
| 待复核 | 信息不足或页面读取失败 |

S/A/B/C 是价值等级，不能代替证据状态。一个 S 级业务线索仍可能不是已确认岗位。

### 5.3 抽查来源得到的结论

- [SFC 官方登记册](https://www.sfc.hk/en/Regulatory-functions/Intermediaries/Licensing/Register-of-licensed-persons-and-registered-institutions)确实提供持牌人士和注册机构查询入口，可作为机构池来源。
- [HK Talent Engage 官方活动页](https://www.hkengage.gov.hk/en/events/global-online-career-fair-june)确认 Global Online Career Fair 2026 的日期为 6 月 21 日至 30 日；在 7 月 1 日报告中只能作为复盘，不是仍可参与活动。
- [小鹏招聘页](https://www.xiaopeng.com/join.html)确认存在社会招聘、校园招聘和外部招聘入口，但页面本身没有显示报告中的 `hr@xiaopeng.com`，联系方式应保存字段级来源，不能因为官网整体可靠就默认每个字段都已验证。
- [HKEX 的 Momenta 招股书](https://www.hkexnews.hk/listedco/listconews/sehk/2026/0629/2026062900057.pdf)确认 Momenta Global 的全球发售和公司主体，但招聘需求属于进一步业务推断。
- Reuters 页面本次抽查无法直接打开，幸好存在 HKEX 官方文件作为更强来源。

这说明 GPT 报告并非不可用，但“一个来源链接支撑整张机会卡”的方式不够严格。ChancePing 应让关键字段分别记录来源或验证状态。

### 5.4 三份新增实际周报带来的补充结论

#### 结论一：它们加强了“聊天优先”，但没有证明“只要聊天”

三份报告都使用类似“再次执行本雷达”的自然语言作为入口，用户不需要重新填写画像。这验证了聊天应成为主入口。与此同时，报告能持续记住项目、作品、目标、禁区、固定来源、评分偏好和输出结构，说明后台必须存在可版本化的长期画像，不能只依赖聊天文本。

因此原判断不变，但证据更强：

```text
聊天负责表达、澄清、确认和调用
结构化后台负责记忆、执行、验证和复现
```

#### 结论二：报告蓝图是雷达画像的一部分，不是导出格式

三份报告都有公共骨架：本轮判断、机会总表、重点详解、风险、行动清单、下一轮监控和来源索引。但真正产生价值的是垂直章节：

- 阿柴雷达会生成 A/B/C/D 四种项目包装方案、62/100 准备度、外联动作和内容选题。
- 文创赛事雷达会判断版权、费用、奖项投入产出和不建议参赛池。
- AI 赛事雷达会给出适配项目、参赛赛道、提交要求和跨赛事复用策略。

所以 ChancePing 不能只有一份固定 Markdown 模板。每个雷达画像应保存一个“公共骨架 + 垂直模块”的报告蓝图，运行时再按本轮结果填充。

#### 结论三：同一个机会必须相对画像评分

广东非遗文创大赛在阿柴雷达中只得到 76 分，在文创赛事雷达中却得到 92 分。两者并不冲突：前者要评估侨批文化数字化项目的材料成熟度和参赛转化，后者更看重工艺、文创和作品适配。

这证明评分不是机会的固有属性，而是：

```text
机会事实 × 当前雷达画像 × 当前项目准备度 = 本轮匹配判断
```

机会基础事实可以复用，但 `OpportunityAssessment` 必须绑定 `radarId + runId + profileRevisionId`，不能把一个全局分数写死在机会本体上。

#### 结论四：需要新增“机会类型”，不能只拆等级和证据

三份报告混合了五类语义不同的内容：

| 机会类型 | 示例 | 客户应如何理解 |
|---|---|---|
| 直接机会 `direct_opportunity` | 有明确报名入口和截止时间的赛事 | 可以立即判断是否行动 |
| 商业线索 `business_lead` | 某国企出现研学采购或合作信号 | 值得联系确认，但不等于已经招标 |
| 参考案例 `reference_case` | 往届获奖项目或行业案例 | 用于改造方案，不应混入报名机会 |
| 观察信号 `watch_signal` | 预告、趋势、即将开放的计划 | 本轮监控，不应承诺可行动 |
| 淘汰项 `rejected` | 已截止、资格不符或成本过高 | 保留淘汰理由，默认不占推荐位 |

这个维度与价值等级、证据状态、行动状态是正交的。例如，一个 `business_lead` 可以是 S 级、证据已核实、行动状态为立即联系，但它仍不是“已确认采购机会”。

#### 结论五：行动建议必须包含准备缺口，而不是一句“建议报名”

实际报告的有用部分通常包括：需要补什么材料、项目应该怎样包装、先联系谁、使用哪个作品版本、如何复用提交材料。ChancePing 的行动输出至少应包含：

- 本轮建议动作。
- 行动前置条件。
- 当前材料或能力缺口。
- 推荐包装方案。
- 联系或提交路径。
- 最晚行动时间。

这些内容应由“客户画像 + 项目准备度 + 机会要求”共同生成。

#### 结论六：风险核验必须覆盖所有权利义务，不能只看版权归属

官方来源抽查验证了三份报告的大部分核心时间、奖金和参赛要求，但也发现了两个值得进入产品规则的例子：

- [DIA 官方规则](https://www.di-award.org/zh/rules.html)除说明参赛者保留知识产权外，还规定现金获奖作品原则上需向主办方赠送实物，并由参赛者承担运输、保险和海关费用。原报告把它概括为“版权风险较低”不算错误，但遗漏了可能影响决策的非版权义务。
- TCAMP 的公开报道可以确认全国开放报名、五大赛题和文创方向，但本次未从可读取的官方材料中核实报告所写的 8 月 15 日截止时间。系统应把该日期标为“待复核”，而不是因为机会整体可信就把所有字段都标为已确认。

这说明每个垂直雷达除评分策略外，还需要轻量 `RiskPolicy`。比赛类至少核验费用、获奖后义务、知识产权、实物交付、差旅、数据公开和材料真实性；BD 类则核验线索是否公开、联系人来源、隐私和推断边界。

本轮官方来源抽查摘要：

| 报告机会 | 抽查结果 | 对产品的启示 |
|---|---|---|
| [腾讯游戏开发者大会 2026](https://gameinstitute.qq.com/awards2026) | 赛期、奖金、AI 游戏赛道和工具支持可从官网核实 | 明确事实可进入已确认机会 |
| [越秀区非遗文创大赛](https://www.yuexiu.gov.cn/gzyxwglt/gkmlpt/content/10/10839/post_10839529.html) | 截止时间、免费参赛和知识产权条款可核实 | 权利条款应逐字段保存，不只写“有版权风险” |
| [TRAE 零代码比赛](https://forum.trae.cn/t/topic/22548) | 报名时间、提交形式和奖励可从官方社区核实 | 官方社区可作为一级来源，但仍需记录页面类型 |
| [Qwen Code with Qwen](https://qwencloud-hackathon.devpost.com/) | 截止时间、五条赛道、现金和云资源总奖励可核实 | “总奖励”和“现金奖励”必须拆成不同字段 |
| DIA | 核心日期和知识产权可核实，但报告遗漏获奖实物赠送和物流义务 | 风险策略必须检查非版权义务 |
| TCAMP | 项目和赛题方向可信，报告中的精确截止日期未完成核实 | 单个字段可以待复核，不拖累整条机会 |

#### 结论七：实际周报适合作为黄金样例，不适合作为客户模板

三份报告证明 ChancePing 可以从统一工作流服务不同客户，但它们不应变成首页的三个固定行业按钮。正确用途是把它们拆成回归测试：同一输入能否生成正确画像、正确搜索计划、正确机会类型、可解释评分、垂直报告章节和字段级证据。

## 6. 三种产品路线

### 路线 A：维持当前多步骤 MVP

```text
首页输入 → 澄清闸门 → 画像确认卡 → 结果页 → 保存 → 我的雷达
```

优点：状态清楚，便于工程测试。  
缺点：用户需要理解产品流程，体验明显重于 GPT；澄清卡容易变成问卷。

判断：不推荐作为客户主路径，但内部状态机可以保留。

### 路线 B：完全复刻 GPT 的纯聊天

```text
用户说话 → 模型自行理解和搜索 → 返回 Markdown
```

优点：最快、最自然、操作成本最低。  
缺点：画像容易丢失，搜索覆盖不可控，评分不可回放，来源和历史关系薄弱，难以稳定服务多用户。

判断：不推荐。它复制了 GPT 的体验，也复制了 GPT 的不稳定。

### 路线 C：聊天优先的结构化雷达产品

```text
聊天交互
→ 后台结构化画像和会话状态
→ 后台搜索计划、证据、评分和报告
→ 聊天中返回卡片和 Markdown
→ 长期雷达、历史和重跑由系统保存
```

优点：操作接近 GPT，同时具备产品级持久化、可重复运行和可审计性。  
缺点：需要重新收敛前端主路径，并统一会话和雷达状态。

判断：**推荐。**

## 7. “聊天即产品”的具体界面

### 7.1 第一屏

第一屏不再是首页表单，而是一个完整聊天工作区：

```text
顶部：当前雷达名称 / 新建雷达 / 我的雷达

中间：对话时间线
  AI 欢迎语
  用户需求
  AI 澄清
  雷达理解摘要
  执行进度
  机会卡片
  报告摘要与文件

底部：自由输入框 + 文件上传 + 发送
```

空白会话可以用三条浅提示教育用户，例如：

- 帮我盯未来 30 天可报名的乒乓球比赛。
- 帮我们找近期可能采购研学服务的国企或学校。
- 读取这份公司介绍，帮我设计一个客户机会雷达。

这些只是输入示例，不是雷达类型。

### 7.2 首次建立雷达

推荐对话：

```text
用户：我们是一家研学文旅公司，想找有研学需求的国企和企业。

AI：明白了。你们想找的不是旅游资讯，而是可能采购研学、红色教育或团队学习服务的客户线索。
    你们准备优先做哪个地区？

用户：广东，广州周边最好。

AI：我会优先关注广东国企、学校和大型企业公开发布的采购、招标、合作征集、职工培训和活动计划，
    排除普通旅行广告。先按未来 30 天搜索，可以吗？

用户：可以，执行。
```

最后一条 AI 回复同时完成画像确认。无需跳转到独立确认页。

### 7.3 再次运行

已保存雷达中，用户可以直接输入：

```text
执行本周雷达
```

或点击输入框上方快捷动作：

```text
本周运行
调整关注范围
补充来源
查看上次报告
```

系统直接读取已确认画像，不再重复提问。只有用户的新指令与旧画像冲突，或关键字段确实缺失时才澄清。

### 7.4 执行过程

聊天中显示一条可更新的运行消息：

```text
正在制定本轮搜索计划
正在搜索 4 组主题、8 个重点来源
已读取 23 个候选页面
正在验证截止时间和来源
已筛出 5 条正式机会、3 条待复核线索
正在生成报告
```

默认不展示 provider 和原始 query。用户展开“本轮搜索范围”时，可以看到查询主题、重点来源和失败来源。这是轻量运行回执，不扩展成 V1.7 来源管理后台。

### 7.5 结果交付

AI 先发送一句总判断，再发送机会卡片和报告文件：

```text
本周发现 2 条值得立即行动的机会，另有 3 条可继续跟踪。
最值得推进的是……，因为……。
```

机会卡片展示：

- 证据状态：已确认机会 / 可行动线索 / 观察信号 / 待复核。
- 价值等级：S/A/B/C。
- 标题。
- 为什么适合你。
- 时间状态。
- 建议动作。
- 官方来源。

完整 Markdown 作为聊天附件，同时可以展开、复制和下载。

## 8. 对当前设计稿的保留、移除与改造

### 8.1 必须保留

1. `RadarRequirementSpec` 作为长期画像的事实来源。
2. 自由文本和文件输入。
3. AI 在信息不足时澄清。
4. 用户确认后才执行首次搜索。
5. 画像驱动的搜索计划。
6. 多来源搜索、抓取、去重和验证。
7. 指定来源 MVP-light。
8. S/A/B/C 分级。
9. “为什么适合我”和行动建议。
10. 机会卡片和 Markdown 双交付。
11. 雷达、run、机会、报告之间的持久化关系。
12. 免费用户 3 个长期雷达。
13. 空结果报告和失败降级。
14. `api.env` 只在本地显式加载。
15. 原 Task 5-8 与 V1.7 继续暂停。

### 8.2 从客户主路径移除

这里的“移除”是从主交互隐藏，不是立刻删除代码：

1. 独立首页表单流程。
2. 独立澄清闸门页面。
3. 一次显示最多 3 个固定问题的问卷式交互。
4. 独立画像确认页面。
5. 把 completeness 和 confidence 数字展示给客户。
6. 用户首次使用时理解“首页、结果页、我的雷达”三个页面的要求。
7. 客户可见的 provider、RadarKind、原始 spec 和评分调试字段。
8. 将大量行业示例作为模板入口。

### 8.3 必须改造

#### 改造 1：确认卡改为聊天内“雷达理解摘要”

仍然需要确认，但用一条自然语言消息完成。客户可以回复“执行”“不对，我想改成……”或点击轻量操作。

#### 改造 2：澄清闸门改为会话策略

保留最多 3 轮、每轮一个关键问题和默认继续，但由后端会话管理，前端不再用狭窄关键词表决定主要语义。

#### 改造 3：新增运行意图

会话至少识别：

- `CREATE_OR_UPDATE_RADAR`
- `RUN_RADAR`
- `ADJUST_RADAR`
- `ADD_SOURCE`
- `EXPLAIN_RESULT`
- `EXPORT_REPORT`

#### 改造 4：评分改成两层

第一层是所有雷达共有的硬门槛：

- 时效。
- 资格或对象匹配。
- 来源证据。
- 必须排除条件。

第二层是画像生成的垂直评分策略：

- 比赛雷达：奖金、背书、参赛成本、版权、材料成熟度。
- 文创雷达：版权、费用、行业认可、商业转化、作品适配。
- BD 雷达：商机、交付、线索完整度、可触达性。
- 研学雷达：采购可能性、预算信号、服务匹配、地域、触达路径。

等级阈值仍由 ChancePing 统一，避免不同雷达各自定义 S/A/B/C。

#### 改造 5：等级和证据状态分离

```text
机会类型：直接机会/商业线索/参考案例/观察信号/淘汰项
价值等级：S/A/B/C
证据状态：已确认机会/可行动线索/观察信号/待复核
行动状态：立即行动/准备/继续盯/放弃
```

四者不能混成一个字段。机会类型说明“它是什么”，证据状态说明“我们确认到什么程度”，价值等级说明“它对当前画像有多重要”，行动状态说明“客户现在应做什么”。

#### 改造 6：报告改为公共骨架 + 垂直章节

所有报告共有：

- 本轮总判断。
- 雷达画像摘要。
- 重点机会总表。
- 重点机会详解。
- 风险和待复核项。
- 本周行动清单。
- 下一轮监控重点。
- 来源索引。

画像可以追加垂直章节，例如：

- 比赛雷达的材料成熟度和参赛方案。
- 文创雷达的版权与费用风险。
- BD 雷达的联系人角色、候选人关键词和话术。
- 研学雷达的采购方式、预算信号和客户触达路径。

每个画像保存 `RadarReportBlueprint`。它只定义章节、必填信息和排序原则，不提前硬编码整篇报告文案。

#### 改造 7：搜索执行留痕

后台保存：

- 本轮搜索主题。
- 实际查询词。
- 指定来源是否检查。
- 打开的 URL。
- 抓取成功或失败。
- 字段来自哪个来源。
- 候选项为何被淘汰。

客户默认只看简化运行回执，工程验收和问题排查使用完整日志。

#### 改造 8：把四份 GPT 雷达变成黄金测试样例

这四份资料不应做成客户可见模板，而应转换为：

- 画像生成测试。
- 搜索计划测试。
- 垂直评分策略测试。
- 报告蓝图测试。
- “不得错域”浏览器验收。

至少覆盖：

1. 文化项目机会。
2. AI 赛事。
3. 非遗文创赛事。
4. 猎头 BD 线索。
5. 乒乓球比赛。
6. 研学文旅客户线索。

#### 改造 9：增加项目准备度快照

长期画像描述客户通常拥有什么和想做什么；`ProjectReadinessSnapshot` 描述客户这一次真正能拿去行动的项目、作品、资质、材料和缺口。它随会话和运行更新，不应把一次性的“62/100 准备度”写死进长期画像。

准备度至少支持：

- 可复用项目或作品。
- 已有资质和证明材料。
- 当前缺少的材料。
- 可投入时间、预算和人员。
- 不同包装方案及其适配机会。

#### 改造 10：字段级证据与垂直风险规则

`EvidenceRecord` 不只绑定整张机会卡，而要能绑定截止时间、费用、资格、奖金、版权、获奖义务和联系人等关键字段。每条证据保存来源、原文摘录或结构化摘要、抓取时间、验证状态和冲突情况。

每个画像还应生成轻量 `RiskPolicy`，规定该行业必须核验哪些决策字段。MVP 不做复杂规则管理后台，由 AI 生成、系统保存并在报告中解释即可。

## 9. 建议的后台对象

聊天优先并不意味着所有内容存成聊天文本。建议后台保持以下对象：

```text
RadarConversation
  负责自然语言消息、文件和当前会话状态

RadarRequirementSpec
  负责长期画像、约束、来源、风险和输出偏好

RadarProfileRevision
  记录用户何时修改了哪些长期理解

RadarReportBlueprint
  负责公共报告骨架、垂直章节和排序规则

ProjectReadinessSnapshot
  负责本轮可用项目、作品、材料、资源和准备缺口

RadarSearchPlan
  负责本轮主题、查询词、语言、域名和时间范围

RadarRun
  负责执行状态、运行日志、结果和报告绑定

OpportunityCandidate
  负责搜索阶段的原始候选和来源

OpportunityAssessment
  绑定 radarId、runId 和 profileRevisionId，负责机会类型、证据状态、价值等级、行动状态、各维评分和评分理由

EvidenceRecord
  负责关键字段的来源、抓取时间、验证状态和冲突记录

ReportArtifact
  负责 Markdown 内容、文件和报告模板版本
```

聊天只是这些对象的交互投影。

## 10. 新版 MVP 主闭环

### 10.1 首次创建

```text
打开聊天
→ 自由描述或上传文件
→ AI 自然复述并按需一次一问
→ AI 在聊天中给出雷达理解摘要
→ 用户回复“执行”或修改
→ 后台冻结本轮画像版本
→ 执行搜索、验证、评分
→ 聊天中返回总判断、卡片和 Markdown
→ 用户选择保存为长期雷达
```

### 10.2 已保存雷达

```text
打开已有雷达聊天
→ 输入“执行本周雷达”或点击“本周运行”
→ 直接读取已确认画像
→ 执行并返回新报告
→ 与上一次运行做最小变化提示
```

MVP 不必实现复杂周环比，但至少应避免把同一旧机会每次都当成“新发现”。

### 10.3 临时结果与长期保存

继续保留“先看结果，再决定保存”的原则：

- 首次画像和运行保存在会话草稿中。
- 不占长期雷达配额。
- 用户点击保存后，创建 custom 雷达并立即运行一次绑定长期雷达的记录。
- 免费用户最多保存 3 个长期雷达。

## 11. 新版 MVP 验收标准

### 11.1 新用户体验

用户无需理解页面、雷达类型、画像字段和 provider，只通过聊天可以完成：

```text
描述需求
→ 回答最多 3 个自然追问
→ 确认理解
→ 执行
→ 查看机会卡片
→ 下载 Markdown
→ 保存长期雷达
```

### 11.2 已有用户体验

已保存雷达中输入：

```text
执行本周雷达
```

预期：

- 不重复询问已确认需求。
- 直接执行。
- 返回本轮运行回执、机会和 Markdown。
- 新结果绑定同一个 radarId 和新的 runId。

### 11.3 泛化能力

以下场景必须使用同一套聊天主链路：

- 乒乓球选手找赛事。
- AI 创作者找比赛。
- 非遗公司找文创赛事。
- 猎头找 BD 和岗位信号。
- 研学公司找采购或合作客户。

不得依靠前端模板选择行业，也不得回退成 RPA 或 AI 赛事默认结果。

### 11.4 搜索可信度

- 正式机会至少有一个可访问来源。
- 关键时间、资格、费用、版权或联系人字段带验证状态。
- 业务推断不能标成已确认机会。
- 直接机会、商业线索、参考案例、观察信号和淘汰项不能混为同一种结果。
- 同一机会面对不同画像时允许得到不同评分，但必须能解释子分和画像依据。
- 费用、版权、获奖后义务、实物交付和差旅等决策条件不能因官网整体可信而漏检。
- 无法确认的截止时间等关键字段必须标记待复核，不能继承整张卡片的可信状态。
- 指定来源未检查成功时要明确说明。
- 报告不能为了凑数量生成假机会。

### 11.5 工程闭环

保存长期雷达后继续满足：

```text
机会包含当前 radarId/radarIds
报告绑定 radar_id + run_id
RadarRun.reportId === reportId
我的雷达能看到机会与报告
刷新后数据仍在
```

## 12. 对原设计稿的建议修改幅度

## 14. 最终判断

GPT 雷达证明了用户并不想“操作一个雷达系统”，而是想“拥有一个懂自己的雷达助手”。

ChancePing 的机会不在于做得比 GPT 页面更多，而在于做到两件事：

1. **像 GPT 一样简单**：用户说一句话就能建立、修改和运行雷达。
2. **比 GPT 更可靠**：画像不会丢、搜索可重复、来源可验证、评分可解释、历史可追踪。

因此 MVP 的产品终局不应是多个配置页面，而应是：

> 一个聊天窗口，背后是一套真正可运行、可保存、可验证的机会雷达系统。
